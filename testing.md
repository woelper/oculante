# Release checklist: no regression over 0.9.6
Written on 2026-10-08. All of it before a release, and nothing goes to crates.io before the human tests are through, a published version stays there. The human tests run on pre-release binaries, not on a crates.io version. Each platform is compared with 0.9.6 on the same machine: no worse than before.

Regressions found by measuring:
- [x] GPU memory: the kernel counted more for large images than on 0.9.6, a 144 MP JPEG 1162 -> 2027 MB, most of it a reserve the driver gives up when memory gets tight. Two causes: a texture was reallocated when its mipmaps were made, the old memory kept as a reserve (now allocated once with all levels, `tex_storage_2d`, where the GL has it), and the driver's upload buffers piled up for an image of several tiles (now it waits for each tile's upload). Measured on 2026-10-12 against 0.9.6: 24 MP 278 -> 271 MB, 64 MP gray 206 -> 151 MB, 144 MP 1161 -> 971 MB, the empty window 45 -> 31 MB. UI test `test_mipmaps_switched_on_and_off`.
- [x] Measured again on 2026-10-12 with c1011bf (`scripts/perf/results/next-c1011bf-gpu.json` against `v0.9.6-gpu.json`, Intel GPU through VirtualGL): nothing worse than 0.9.6. Opening a 24 MP JPEG 0.43 -> 0.34 s, 64 MP gray PNG 0.95 -> 0.29 s, memory of the process 40-50 % lower, peak at 24 MP 511 -> 182 MB, GPU memory equal or lower, back to the previous image 0.08 -> 0.04 s, animation CPU 24 -> 12 %, idle 0 % CPU and no wakeups. GPU time for panning a 24 MP image looked 33 % worse in that run, measured alternating with 0.9.6 five times each it is 0.095-0.097 s against 0.101-0.102 s: noise from the GPU clock.

- [ ] Release notes open with the breaking changes, each with what to do about it. Same text on the GitHub release, in the Flathub metainfo and to the packagers below. Known on 2026-10-13:
  - Build features gone: `update`, `notan/shaderc` and `notan_glsl-to-spirv`. Leave them out of `--features`. The FreeBSD port passes `--no-default-features notan/shaderc` and fails to build until it does. `heif` and `dav1d` still work, they give the Rust decoders now.
  - Libraries packages no longer need: libheif, libavif, libdav1d, lcms2, FreeType, fontconfig, GTK, cairo, expat, libwebp. The binary links only libc, plus libturbojpeg with `TURBOJPEG_SOURCE=pkg-config`. To build: Rust 1.98, cmake, nasm and a C compiler.
  - No update check and no self update in the app: updates come from the package manager or the releases page.
  - Only libheif opened these, so they no longer open on macOS and Windows: .heics, .heifs, .avci and .avcs. Camera HIF (4:2:2) and 4:4:4 open again since 2026-10-13, with tbraun96/heic-rs#10 and #12 in the fork.
  - The HEIF security limits are gone from the settings, HEIF is read without a limit like the other formats.
  - X11 window rules on the instance (i3 `instance="oculante"`) no longer match, unless egui-winit is fixed first: match the class, `class="oculante"`.
  - The SVG scale saved by 0.9.6 is not read, it starts at 2. Set it again in the settings.
  - Nothing to do, but say so: everything else in the settings carries over, shortcuts are converted (human test above).
- [ ] Release notes with the changes made on purpose: edits give different pixels than 0.9.6 (rounding, Contrast and Desaturate fixed; Exposure in stops of light, Posterize with the levels it says, a LUT in its place among the pixel filters: saved edits with these look different), 16 bit PNG and AVIF stay 16 bit, HEIC opens without libheif on every platform, camera HIF (4:2:2) and 4:4:4 included (libheif is gone: .heics, .heifs, .avci and .avcs no longer open on Mac and Windows; the HEIF security limits are gone from the settings), JXL colour management with moxcms instead of lcms2, the `dav1d` feature is a second name for `avif_native` (no libavif and libdav1d), system fonts found with fontdb instead of font-kit and FreeType, no update check, SVG scale 2 by default, the info panel opens at its set width, Rust 1.98 to build. Since 2026-10-07: planar TIFFs open (only red before), ORA files without the "Extension mismatch" warning, faster TIFF above 8 bit (and much less memory), EXR and Radiance HDR, images above 512 MB open (#782), JPEGs libjpeg-turbo refuses fall back to the image crate. On macOS two fingers on a trackpad move the image, a pinch zooms (in 0.9.6 two fingers zoomed, a setting brings that back), the noise filter keeps its noise on every change, "New noise" rolls new, the memory for the image cache is a setting (Automatic is as before). New for 1.0: the sequence view (#777), KTX2 in all formats of the KTX-Software tests, Basis Universal without C++.

Things to keep in mind:
Oculante has a multi-stage system to keep textures in memory:
1. Once it is loaded, an image is kept as OculanteState.current_image. It is used to revert edits of the loaded image or enable image editing. It is a DynamicImage, so it can contain more information than we can see (float values etc). It is expensive to keep around as it consumes extra memory in addition to the texture, but I don't know a better way as long as we want to edit images. Perhaps we can get rid of it when we load the image again when entering edit mode and store it in EditState, but is this better?
2. EditState.result_pixel_op: the final edited image. When all edits are done, it should be used to generate the texture.
3. EditState.result_image_op: All image operaters are very expensive as they don't run per pixel and can't be paralellized and SIMD'd. So all image ops are run and cached into this, so the user can scrub and tweak pixel ops freely.
